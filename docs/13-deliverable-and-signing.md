# 交付形态与驱动可改点

2026-11-11。回答两个问题：最终驱动包怎么组织；驱动本身有哪些地方能改。

## 1. 驱动里确实有可改的地方——共 7 处

按「改动量 / 收益」排序。地址均来自 `Netwtw14.sys`（SHA256 `87C08301…38B8`）。

| # | 位置 | 现状 | 改法 | 难度 |
|---|---|---|---|---|
| 1 | `utilOpModeToMacType` `0x1400432a0` | 只映射 1/8/0x10/0x20，**永远不会返回 SNIFFER(5)** | 增加一条映射或放行 OPERATION_MODE → 5 | **低（改常量/分支）** |
| 2 | `prvHmfmHandleActionFrame` `0x1402d70f0` | 类别 `0x7f` 落 `break`，不处理 | 改为走上报路径 | **低（改跳转）** |
| 3 | OID 分派表 `0x52FC60`（146 条） | `OID_SV_EXECUTE_SNIFFER_CMD`=`0x0D01011A` 等已存在但用户态不可达 | 增加一条可从 OS 到达的入口 | 中 |
| 4 | `mhiffSendP2pActionFrameCmdVer2` `0x1403455c0` | 只收帧体（≤`0x21B`），MAC 头由 `0x140141440` 生成 | 让头部地址由调用方给定 | 中 |
| 5 | `rxPacketProcessValidMpduFrame` `0x1400456e0` | 数据帧→`0x1400448b0`，管理帧→`0x140044bb0`，最终都汇到 `0x14000aab0` 上报 | 增加一个旁路出口 | 高（要加代码） |
| 6 | sniffer 子系统（`snifferVifCreateAPI`、`MAC_TYPE_SNIFFER`、radiotap 构造函数、`GRP_DATAPATH_HE_AIR_SNIFFER_CONFIG_CMD`） | 代码存在，但上游没有调用者 | 打通创建 + 输出 | 高（要加代码） |
| 7 | 换台命令族（`mhiffBuildChannelSwitchStartNotifVer3` 等） | 存在，含失败上报 | 暴露给上层 | 中 |

### 关键判断

- **1、2 是「改分支」级别**，可以用等长指令替换完成，不需要新增代码段。这是最有价值的低成本改动。
- **5、6 需要新增代码**（缓冲区拷贝、导出通道），在已签名的二进制里做等于写 code cave，脆弱且难维护。
- 因此现实路线是：**只对 Intel 驱动做 1、2 这类小改动；其余能力由我们自己的伴生驱动承担。**

## 2. 交付形态建议

不建议交付「整个改过的 Netwtw14.sys」。理由：5.6 MB 闭源二进制，任何插入式改动都难以验证，且每次驱动更新都要重做。

建议的包结构：

```
AX201-AirDrop/
  driver/
    ax201awdl.inf        # 安装我们自己的 NDIS 组件
    ax201awdl.sys        # 伴生驱动：发私有 OID、收帧、导出到用户态
    patch/
      Netwtw14.sys       # 仅含 1、2 两处小改动的版本（可选组件）
      patch-notes.md     # 精确到字节的改动说明与还原方法
  app/
    ax201awdl-ui.exe     # 管理界面
    ax201awdl-svc.exe    # 用户态代理，与驱动通信
  install.ps1            # 一键安装/卸载/回滚
  README.md
```

安装后的效果：

- 设备管理器里出现一个独立设备（我们的驱动），不替换 Intel 的网卡驱动
- UI 可以开关 AirDrop 接收、查看 peer、看抓到的帧
- 卸载即恢复，Intel 驱动保持原样（除非装了 patch 组件）

## 3. UI 要做成什么样

参考你给的那个项目的定位——**专用的 AirDrop 管理面板**，不是通用抓包工具。最小功能集：

1. **总开关**：启用/停用 AirDrop 接收
2. **状态区**：当前信道、是否在嗅探、最近一次换台耗时
3. **Peer 列表**：发现的设备、地址、最后活跃时间
4. **接收区**：待接收文件、进度、保存路径、SHA256 校验
5. **诊断区**：驱动版本、OID 调用结果、错误码解码
6. **日志**：滚动显示，可导出

技术上用本地 Web UI（内置 HTTP 服务 + 浏览器）最省事，也便于以后改成远程管理。

## 3.5 签名与 Secure Boot：分两个阶段

这是交付形态里最容易被忽略、但决定「别人能不能用」的一条。

### 现阶段（自用 / 验收）

必须关闭 Secure Boot，而且**不是装的时候关一次**：

- 测试签名是**启动期策略**，写在 BCD 里
- Secure Boot 一旦重新打开，`testsigning` 立即失效，自签驱动不再加载，设备直接起不来
- HVCI 也要保持关闭，否则内存完整性会拦下不兼容的驱动

所以自用阶段是「这台机器长期处于测试签名状态」，不是一次性动作。

### 正式发布

可以做到**不关 Secure Boot**，前提是拿到微软签名：

| 方式 | 要求 | 结果 |
|---|---|---|
| Attestation signing（证明签名） | EV 代码签名证书 + Partner Center 账号，逐个驱动提交 | Secure Boot 开启也能加载，HVCI 兼容需驱动本身合规 |
| WHQL 签名 | 完整 HLK 测试 | 同上，门槛更高 |

成本量级：EV 证书每年数百美元，Partner Center 注册本身免费。

### 但有一个硬限制

**改过的 `Netwtw14.sys` 不能随包发布，也无法签名。**

- 它是 Intel 的二进制，修改后重新分发违反许可
- 微软的签名通道只接受提交者自己的驱动，我们不拥有它

因此可发布的部分只能是**我们自己的伴生驱动 + UI**。Intel 驱动的补丁只能作为本机研究用途存在。

这也反过来强化了一个设计选择：**尽量让伴生驱动通过 OID 完成全部功能，不对 Intel 二进制做依赖**。只有实在绕不过去时，才在本机使用补丁版。

## 3.6 社区版定位下的安装设计

定位是社区版、使用者自行安装，不是商业产品。这带来三条硬约束和一条解法。

### 约束一：Secure Boot 必须由使用者自己关

任何内核组件（我们的驱动或被改过的 Intel 驱动）在自签状态下都需要测试签名，而测试签名要求 Secure Boot 关闭。这是物理操作，安装程序无法代劳，只能**引导 + 检测**。

安装程序应当：

1. 先检测 `Confirm-SecureBootUEFI`
2. 若为真，停止安装，给出带截图的分步指引（进 UEFI → Security → Secure Boot → Disabled）
3. 用户重启后重新运行安装程序，继续

### 约束二：不能分发改过的 Intel 驱动

社区版同样受版权约束。解法是**本地打补丁**：

- 安装包里不放 `Netwtw14.sys`
- 只放补丁脚本与校验清单
- 运行时读取**用户自己机器上**的驱动副本，校验 SHA256 匹配后原地打补丁
- 保留原始文件备份，支持一键还原

这样分发的是「补丁方法」，不是「Intel 的二进制」，法律上干净得多。

同时必须做**版本白名单**：只对已知的驱动版本/哈希应用补丁，版本不符就拒绝并提示。否则不同驱动版本上的偏移全错，会直接把网卡搞坏。

### 约束三：必须能可靠回滚

社区用户没有调试能力。安装程序需要：

- 打补丁前完整备份驱动包并校验
- 创建系统还原点
- 提供 `uninstall.ps1`，能恢复原始驱动并清理测试签名状态
- 失败时自动回滚，并保留日志供反馈

### 解法：让补丁变成可选项

如果伴生驱动能只靠 OID 完成核心功能（发私有 OID、收帧、导出到用户态），那么：

- **默认路径**：只装我们的驱动，不碰 Intel 的
- **增强路径**：需要时再打补丁

这样绝大多数社区用户不必承担改 Intel 驱动的风险，出问题也更容易定位。

## 3.7 使用者要接受什么

必须在 README 顶部用醒目方式写明：

1. 需要关闭 Secure Boot，整机内核安全等级下降
2. 测试签名状态会一直保持，直到手动关掉
3. 补丁组件会修改系统驱动文件（有备份、可还原）
4. 属于实验性项目，可能影响正常 Wi-Fi 使用
5. 只支持特定驱动版本

不写清楚，社区用户装完出问题会全部算在项目头上。

## 4. 必须先解决的前置问题

无论包怎么组织，有一件事没变：**自写驱动要能加载，必须关闭 Secure Boot**。

- 关闭 Secure Boot —— 只能在 UEFI 里做，需要你操作
- 关闭 HVCI、开启测试签名 —— 我可以用提权执行器完成，需重启

在这之前，第 1、2 两处「改分支」的补丁可以**先做出来并静态验证**（字节级 diff + 反汇编复核），但装不上、测不了。

## 5. 建议的推进顺序

1. 先做 1、2 两处补丁，产出可复核的二进制 diff（不需要重启）
2. 同时写伴生驱动与 UI 的骨架
3. 你关 Secure Boot → 我装环境、装驱动、联调
4. 用 iPhone 实测接收链路
5. 打包成可安装交付物

## 6. 仍然存在的未知

- sniffer 的帧最终流向哪里（是否有 OS 可见出口），静态上还没确认
- 固件是否响应 `GRP_DATAPATH_HE_AIR_SNIFFER_CONFIG_CMD`，只有实测能答
- 第 4 处改动后，头部地址是否真能按调用方意愿生效

这些都要等驱动能装之后才能验证。
