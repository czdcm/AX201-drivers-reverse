# 逆向工程经验总结

> 来源：2026-11-11 对 Intel `Netwtw14.sys`（Wi-Fi 6 AX201 驱动）的静态逆向，两小时窗口内完成 13,348 个函数的导出与结构还原。
> 本文只记**可复用的经验**，不复述结论。

---

## 一、工具链：真正会卡住你的地方

### 1.1 Ghidra 装在中文路径下会静默失败

现象：`analyzeHeadless` 启动 6 秒退出，退出码 0，没有任何输出，日志文件根本没生成。

真因：log4j 解析 `jar:file:` URL 时按 ANSI 解码路径，中文变成乱码，`Generic.jar!` 里的日志配置加载失败 → `No logging configuration` → 直接中止。

**解决**：把整个 Ghidra 安装目录复制到纯 ASCII 路径（如 `C:\ProgramData\ghidra122`）。**建目录联接（junction）没用**——Java 会把链接解析回真实中文路径。

### 1.2 `.bat` 必须是 CRLF + ASCII

- 用 LF 写出的 `.bat`，cmd 会把行切碎，报 `'et' is not recognized`（`set` 被咬掉首字母）。
- 用 UTF-8 写含中文路径的 `.bat`，cmd 按 OEM 代码页（936）解析，路径全乱。
- **正确写法**：`[IO.File]::WriteAllText($path, $text, [Text.Encoding]::ASCII)`，且行尾用 `` `r`n ``。

### 1.3 PowerShell 会毁掉中文文件

`Get-Content -Raw` 在中文 Windows 上默认按 GBK 解码 UTF-8 文件 → 读进来已经是乱码 → `Set-Content` 写回就是永久损坏。

本次踩过两次，其中一次把 README 推成了乱码。

**规则**：
- 改文件用编辑类工具，不要用 `Get-Content`/`Set-Content` 组合；
- 必须用 PowerShell 时加 `-Encoding UTF8`（读也要加）；
- 生成文件用 `[IO.File]::WriteAllText(..., New-Object Text.UTF8Encoding($false))`（无 BOM）。

### 1.4 其它小坑

| 坑 | 现象 | 解 |
|---|---|---|
| `Join-Path $a 'x' $b` | 三参数报 `PositionalParameterNotFound` | 嵌套：`Join-Path (Join-Path $a 'x') $b` |
| `"$var:字"` | `InvalidVariableReferenceWithDrive` | `"{0}: {1}" -f $var,$x` |
| `cmd /c "... > file"` | 引号被吃，`> was unexpected` | 写成 `.bat` 文件再调用 |
| 7-Zip 开 Inno Setup | 只当 PE 列节表 | `innoextract`（且需先把 exe 复制到 ASCII 路径） |
| 7-Zip 开 WiX Burn 自定义 BA | `0x80131502` 挂死 | 该安装器不支持 `-layout`，只能放弃 |

## 二、逆向方法：本次最有价值的三条

### 2.1 找到驱动的"命名 Oracle"

闭源驱动通常剥了符号，但**诊断/断言字符串会残留函数名**。本次的 Oracle：

```c
FUN_1400b37e0(moduleId, "Class::Method", sourceLine, siteTag)
```

它被 2,265 处调用，本质是**断言/看门狗检查点记录器**（写 50 槽环形缓冲 + `NdisWriteErrorLogEntry`）。

一次正则扫描，13,348 个函数里救回 **2,246 个真名（16.8%）**，而且带**类名**（`osal::CCmdProperty::execute`）——直接给出对象模型。

**这条经验的推广**：任何大型闭源二进制，先找"带字符串常量的错误处理/日志/断言函数"，它往往是唯一的符号残留。

### 2.2 用 vptr 安装现场恢复虚表，不要指望 RTTI

本次驱动用 `/GR-` 编译，**全文件 0 处 RTTI 修饰名**，`vtable[-1] → COL → TypeDescriptor` 完全走不通。

改用 **MSVC 构造/析构的标准形态**：

```asm
LEA RAX, [0x1403e71e8]     ; vftable 地址
MOV qword ptr [RCX], RAX   ; *this = vftable
```

在 13,348 个 `.asm.txt` 里匹配"LEA 后 1–3 条指令内写入对象"，拿到 **344 个安装点、125 张确认虚表**，补出 **562 条被遮蔽的间接调用边**。

**副产品结论**：补边后原 Top 12 入度榜一个都没变 —— 这是检验补边算法有没有污染图的好指标（热点靠直接调用就有几千入度，不该被间接边改变）。

### 2.3 大数据表要从原始字节读，不要从反编译读

固件命令表、参数描述符表这类**静态数据表**，Ghidra 的 `.c` 里只能看到零散引用。

正确做法：解析 PE 节区表，把 VA 映射成文件偏移，直接 dump 原始字节。

本次关键校验：`VA 0x1405B6060 → 文件 0x536460`（`.text` RVA 0x1000/文件 0x800，`PAGEdBla` RVA 0x5B6000/文件 0x536400），一次读出 118 条命令描述符。

**注意**：VA→文件偏移**不能**用 `VA - ImageBase` 硬算（除非节区恰好对齐）。必须按节区 `VirtualAddress` / `PointerToRawData` 换算。本次先用错方法，读到一屏垃圾。

## 三、并行策略

### 3.1 Ghidra 项目是独占的

同一个项目目录开两个 headless 会锁冲突。做法：**复制项目**（`.gpr` + `.rep`，约 94 MB/份），N 个实例各用一份。

本次 6 份副本、6 路并行，53.6 秒导完 13,348 个函数（单实例约 5 分钟）。

### 3.2 子智能体分工：按簇分，但要求它们自查前提

9 个子智能体各领一簇（wdi-osal 太大拆两半），产出 12 份模块报告。

**有效的做法**：
- 明确告诉它们"文件在哪、每个文件的结构是什么"，不要让它们自己找；
- 要求"只读磁盘、不读会话历史"——避免上下文膨胀；
- 要求"推断必须标注、没看懂写没看懂"——本次 8 份报告都诚实列了未解项。

**意外收获**：子智能体会**反过来纠正任务书里的错误假设**。三条最有价值的修正（`FUN_1400b37e0` 是断言不是日志、AddSta=778 不是 435、`0x140043fcd0` 不是虚表）都来自它们。

### 3.3 上下文预算

13,348 个文件不可能读进上下文。做法：

- 全部落盘，只在上下文里传**路径、统计数字、索引表**；
- 子智能体返回**摘要 + 关键发现**，不返回原文；
- 报告里区分"导出覆盖"与"理解覆盖"，前者 100%，后者 5%。

## 四、必须警惕的认知陷阱

| 陷阱 | 后果 | 教训 |
|---|---|---|
| **把地址聚类当模块划分** | 一个大簇横跨十余个子系统，报告全是废话 | 用 **tag（编译单元 ID）** 做模块划分，地址段只是分工手段 |
| **低去重率否决虚表** | 误杀 13 张真虚表 | 本驱动大量方法共用空桩（`_purecall` 被引用 431 次），21% 去重率的真虚表确实存在 |
| **大指针表当虚表** | `0x140043fcd0`（3,382 条目）会灌进 3,382 条假边 | 它是**寄存器访问器分派表**；判据：条目数、去重率、目标集中度 |
| **tag 当函数边界依据** | 同一 TU 多函数共用 tag，会切错 | tag 只能推"属于哪个源文件" |
| **信 Ghidra 的参数个数** | 多处栈参数被丢失（`0x14005cf40` 有 10 参，调用点只见 4 个） | 关键函数必须对照 `.asm.txt` |
| **信 Ghidra 的函数总数** | `.pdata` 有 15,741 条，Ghidra 只建了 13,348 个 | 差的是 ICF 折叠/链式函数，可能漏 15% |
| **凭记忆对 cmdId 与命令名** | 两处错配（435/778、512/264） | 必须从构造函数断言串重建映射 |

## 五、工程组织

### 5.1 产物分层

```
原始证据（可重跑）  →  out/p1..p6（26,712 个 .c/.asm）
中间索引（结构化）  →  out/meta、out/clusters、out/graph
分析报告（人读）    →  out/modules/*.md、docs/*.md
仓库（可发布）      →  报告 + 数据表 + 脚本 + 清单
私有归档（不发布）  →  反编译原文、字符串转储（著作权风险）
```

### 5.2 每个产物都写 manifest

`data/manifests/full-re-manifest.json`：路径、字节数、sha256 前 16 位、统计总数。

好处：日后发现某个数字不对，能立刻定位是哪一版产物。

### 5.3 脚本必须可重跑

`run-all.ps1 -SkipExport` 这类开关要有；批处理里所有路径写绝对；每个脚本自带日志输出。

本次全流程重跑只需 183 秒，这让"先干跑一遍验证"成为低成本动作——**第二小时的所有分析都建立在白天已经验证过的流水线上**。

## 六、决策经验

### 6.1 先验证决定性前提，再投入工作量

本次项目（AirDrop 接收）最终失败的根因不是技术深度，而是**两个无法绕过的约束**（Secure Boot 必须开 + 驱动必须微软签名）。

早点把这类前提列出来，可以省掉整轮开发。

### 6.2 时间是资源，也是借口

两小时窗口里，真正的瓶颈是**上下文预算**，不是 CPU。先算清楚"能读多少个函数"，再决定分工——而不是先开工再看。

### 6.3 诚实标注覆盖率

"导出 100% / 读懂 5%"这句话必须写在报告第一页。否则读者会以为 13,348 个函数都被理解了，那是误导。

## 七、可复用的检查清单

新接一个内核驱动逆向任务时：

- [ ] 文件版本、哈希、Package 版本要分清（本次包版本 24.50.0.4 ≠ 二进制版本 23.50.21.2）
- [ ] 先看导入表，确认框架（WDI miniport？WDM？KMDF？）
- [ ] 找命名 Oracle（断言/日志/`__FUNCTION__`）
- [ ] 统计函数总数（Ghidra）并与 `.pdata` 条目数对照
- [ ] 恢复虚表（vptr 安装现场）
- [ ] 找静态数据表（命令表、参数表），从原始字节读
- [ ] 建立 tag/编译单元 → 子系统的映射
- [ ] 画调用图，检查高度数节点是否是基础设施（日志/内存/锁）
- [ ] 用导出覆盖率和阅读覆盖率两个数字描述进度
