# AX201 OID 分派表还原

2026-11-11。只读静态分析，数据来自 `Netwtw14.sys`（SHA256 `87C08301…38B8`）。未执行任何 OID、未改驱动。

## 1. 表结构

在 `.rdata` 中发现一张连续的 OID 分派表，起始文件偏移 `0x52FC60`，**146 条**，每条 `0x50` 字节：

| 相对偏移 | 宽度 | 含义 |
|---|---|---|
| 0x00 | 0x40 | OID 名称（ASCII，NUL 填充） |
| 0x40 | u32 | **OID 数值**（小端） |
| 0x44 | u32 | 保留（全 0） |
| 0x48 | u64 | **处理函数指针** |

完整列表见 oid-table.txt（制表符分隔：名称 / OID / 处理函数）。

验证方式：表中 `OID_802_11_BSSID_LIST_SCAN` 对应 `0xFF800000`，与 Windows 标准 OID 定义一致，说明偏移解释正确。

`0xFF6000xx` 这一整段（`OID_SET_*`）明显是 Intel 内部测试钩子：固定速率、TWT、SMPS、MLD 链路选择、动作帧发送等。

`OID_SV_DIRECT_ACCESS` / `OID_SV_INDIRECT_ACCESS` / `OID_SV_PCI_CFG` 属于厂商诊断接口，在量产驱动里保留，通常是给产测/调试工具用的。**这三条的威胁等级远高于 sniffer**——若可达，等于获得了设备内存与 PCI 配置的读写。本次只做记录，未尝试。

## 3. 嗅探命令入口的真实行为

`0x140158F50` 的实际逻辑：

1. 校验请求的 OID 是否为 `0x0D01011A`；
2. 只接受 method 类型 `5` 或 `2`，其余一律 `0xC0000001`；
3. 不读取调用方缓冲区中的信道/带宽/频段参数；
4. 自行构造一个 `0x7C` 字节结构：首 DWORD = 3、6 字节地址、状态码、时间戳、`0x24` 字节载荷；
5. 转手以 **OID `0x0D01030B`** 发出。

结论：**这条 OID 不是「设定信道并启动嗅探」的入口**。它更像一次能力/状态握手，真正的参数化命令走 `0x0D01030B`。

`0x0D01030B` 不在名称表中（全文件只有一处立即数引用），是内部构造的 OID，因此无法从名字反查，需要从处理函数往下追。

## 4. 目前仍缺的东西

要到「能启动嗅探并取到帧」，还差：

1. `0x0D01030B` 的处理路径与它期望的载荷结构；
2. `SNIFFER_CMD_ARGUMENTS`（`snifferCmd` / `controlChannel` / `channelWidth` / `band`）到底在哪个函数里被解析；
3. **这些 OID 如何从用户态触达**——`WlanIhvControl` 只映射到 NIC-specific OID（`0x0D01035C`），并不能直接发送表中任意 OID。

第 3 点是决定性的：即使知道全部 OID 数值，若没有一条合法路径把它们送进驱动，静态分析再深也无法落地。

## 5. 下一步建议

优先解决第 3 点，而不是继续深挖第 1、2 点。具体做法：

- 查驱动是否暴露**设备接口 / IOCTL / WMI** 供这些 `0xFF6000xx` 测试 OID 使用；
- 确认 `OID_SV_COMMAND`（`0xFF400008`）是否为通用命令通道，能否携带任意子命令；
- 若确实只有 NDIS 一条路，则回到「自写 NDIS 过滤器直接下发 OID」的方案——那需要测试签名。

在解决「怎么送进去」之前，继续还原嗅探参数结构属于边际收益很低的工作。
