# 关键发现：嗅探帧经 ETW 输出

2026-11-11。只读静态分析。这条发现改变了可行性判断。

## 1. 接收路径的真实结构

`FUN_1400450e0(adapter, packetDesc)` 是接收分发入口，它按一个模式标志分叉：

```
if ( *(int *)(*(adapter + 0xcf68) + 0x28) == 0 ) {
    FUN_14007f1a0(...);          // 正常处理
    FUN_1400456e0(adapter, pkt); // 交给常规接收路径 → 最终上报操作系统
    return;
} else {
    FUN_1400512d0(...);
    FUN_140071a30(pkt);          // ← 构造 radiotap，写入 ETW
    local_28[0] = 1;             // 标记为"已消费"
}
FUN_140044460(..., pkt, 0);      // 释放该包
```

也就是说：**当那个标志非 0 时，收到的帧不再上报系统，而是被转成 radiotap 事件写进 ETW，然后丢弃。**

这个分支就是嗅探/监听模式。

## 2. ETW 事件的构造链

`FUN_1400450e0` → `FUN_140071a30(pkt)`

`FUN_140071a30`：
1. 在栈上开 0x200 字节缓冲
2. 调 `FUN_1401a6e80` 构造 radiotap 头（含 TSFT、flags、rate、channel、MCS/VHT/HE 等字段，分别由 `FUN_1401a7d80`、`FUN_1401a7ec0`、`FUN_1401a79e0` 追加）
3. 若 `DAT_1404cc800 & 1` 非零，调用 `FUN_1400720a0(&providerHandle, &eventDescriptor, ...)`

`FUN_1400720a0` 最终调用 **`EtwWriteTransfer`**。

结论：**帧数据（radiotap + 802.11 帧）通过 ETW 事件对外输出。**

## 3. 为什么这条很重要

ETW 是**用户态可以消费的**。管理员可以开一个 trace session，订阅对应 provider，实时收到事件。

这意味着：

- **不需要为新驱动实现数据通道**
- 内核侧只需要做一件事：**把那个模式标志置上**
- 帧的搬运完全交给现有的 ETW 机制

架构因此简化成：

```
[极小的内核组件]  ──发一条私有 OID──▶  Intel 驱动置位嗅探模式
                                          │
                                          ▼
                                  收到帧 → radiotap → ETW
                                          │
                                          ▼
[用户态程序] ◀── 订阅 ETW ────────────────┘
     │
     └── 解析帧 → AWDL 协议栈 → UI
```

## 4. 但仍然绕不开签名

置位那个标志只有一条路：发私有 OID（`OID_SV_EXECUTE_SNIFFER_CMD` 或对应的内部命令）。

用户态发不了（前面已实测排除三条路径），所以**仍然需要一个内核组件**——哪怕它只做「发一条 OID」这一件事。

内核组件就要签名。而「使用阶段不关 Secure Boot」只接受微软签名。

## 5. 因此最终判断

| 方案 | 使用阶段要关 Secure Boot？ | 可行性 |
|---|---|---|
| 改 Intel 驱动 | 要（且永远签不了名） | 不可交付 |
| 自签伴生驱动 | 要 | 仅限自己用 |
| **微软签名的极小伴生驱动 + ETW 消费** | **不要** | **技术上成立，取决于能否拿到签名** |

所以项目**不是技术不可能**，而是卡在签名这一关：

- 有 EV 证书 + Partner Center → 可交付、用户不用关 Secure Boot
- 没有 → 只能自用，或要求用户关 Secure Boot

## 6. 仍未验证的三件事

1. 协议驱动能否向 WDI 小端口发送非标准 OID（Npcap 失败是它自己的白名单，不能代表我们自己写的驱动）
2. `OID_SV_EXECUTE_SNIFFER_CMD` 的确切请求体格式
3. ETW 事件的速率与时延是否满足 AWDL 的时序要求（AWDL 本身是低速协议，同步约 24 帧/秒，理论上够用）

这三件事都必须在驱动能加载之后才能验证，也就是必须先解决签名或临时关 Secure Boot。
