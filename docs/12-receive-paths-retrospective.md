# 复盘：接收 AirDrop 的全部可能路径

2026-11-11。约束前提：不加新硬件；使用阶段 Secure Boot 保持开启（安装时临时关闭可接受）；不依赖 Apple 签名完成"发送"。

## 1. 先说结论

**接收 AirDrop 并非只差"发送"这一环。** 它至少受三道独立的门限制，任何一道过不去，后面全无意义：

| 门 | 内容 | 现状 |
|---|---|---|
| 门 1 | Apple 是否要求接收方身份由 Apple 签发 | **未验证，且可能一票否决** |
| 门 2 | 能否拿到空口原始 802.11 帧 | 已知需内核组件 |
| 门 3 | 内核组件能否在 Secure Boot 开启时加载 | 需微软签名或 UEFI 自定义密钥 |

社区讨论里经常只谈门 2 和门 3，但门 1 才是真正的分水岭。

## 2. 已实测排除的路径

这些不是推测，是做过实验的：

| 路径 | 结果 |
|---|---|
| `WlanIhvControl`（service 类型） | `ERROR_DEV_NOT_EXIST` —— 无 IHV 服务上下文 |
| `WlanIhvControl`（driver 类型） | `ERROR_NOT_SUPPORTED` —— WDI 驱动不实现 Native 802.11 OID |
| 放开 DACL 后重试 | 仍失败，说明限制不在 ACL |
| Npcap `PacketRequest` + 私有 OID | `INVALID_OID` / `NOT_SUPPORTED`，只放行标准 NDIS OID |
| IHV 扩展 DLL 路径 | DLL 侧无客户端校验，但服务后端不存在 |

**结论：用户态没有任何一条路能把私有命令送进 AX201 驱动。**

## 3. 接收路径清单

### 路径 A：微软签名的极小内核驱动 + ETW 收帧

**做法**：自写一个只做两件事的驱动——发一条私有 OID 打开嗅探模式、必要时发动作帧命令。帧数据由驱动已有的 ETW 通路输出，用户态订阅 ETW 消费。

**证据支撑**：`0x1400450e0` 在嗅探模式下把帧转成 radiotap 事件，经 `FUN_140071a30` → `EtwWriteTransfer` 输出；`FUN_1401a6e80` 负责拼 radiotap。

**优点**
- 完全符合"Secure Boot 开启 + HVCI 开启"
- 驱动极小，面世风险低
- 不修改 Intel 驱动，不分发第三方二进制

**代价/风险**
- 需要 EV 证书 + Partner Center 做 attestation 签名
- 私有 OID 能否被 WDI 小端口受理，**未验证**
- ETW 事件的速率、时延、是否含完整帧，**未验证**

**这是唯一同时满足全部约束的路径。**

### 路径 B：把自签证书写进 UEFI db

**做法**：安装时临时关 Secure Boot → 进 Setup Mode → 把自签根证书写进 db → 重新开启 Secure Boot。此后自签驱动可加载。

**优点**：不需要微软签名，成本为零。

**风险**
- 多数 OEM 笔记本锁死密钥管理，需要清除 Platform Key，操作失误可能导致无法启动
- 每个用户都要做一遍，比关 Secure Boot 更危险
- HVCI 仍需驱动本身兼容

**适用性**：只适合愿意承担风险的少数用户，不适合社区版默认路径。

### 路径 C：临时关闭 Secure Boot（已排除）

技术上最容易，但按你的约束不成立。

### 路径 D：修改 Intel 驱动

**永久排除**：签不了名、违反许可、无法分发。即使自己用，也要求 Secure Boot 关闭。

### 路径 E：纯用户态

**已证明不存在**（见第 2 节）。

## 4. 非 AWDL 的替代思路

这些不是 AirDrop，但值得列出来，因为它们可能满足"从 iPhone 拿文件"的真实需求：

| 思路 | 能否收 AirDrop | 说明 |
|---|---|---|
| BLE 广播伪装的 AirDrop beacon | **不能** | 只让设备出现在候选列表，传输仍需 AWDL 链路 |
| 基础设施模式（同一 Wi-Fi） | **不确定** | 苹果未公开支持非苹果设备；不能作为方案依据 |
| iPhone USB 共享 + 文件 App | 不是 AirDrop | 可行但与目标无关 |
| 局域网 HTTP/自建传输 | 不是 AirDrop | 需要发送方配合 |
| Mac / 树莓派做 AWDL 桥 | 是 AirDrop | 但属于新硬件，已排除 |

## 5. 门 1 才是真正的未知

所有路径都建立在一个未验证的假设上：**iPhone 愿意把文件推给一个没有 Apple 签发身份的 AWDL peer。**

AirDrop 的发现记录中包含身份信息，iPhone 侧会做校验。如果该校验要求 Apple 签发的证书，那么：

- 无论驱动做得多好，设备都不会出现在发送方的 AirDrop 列表里
- 接收路径全部失效

**这一条无法在本机单独验证**——验证它本身就需要先能发出 AWDL 帧。这是典型的先有鸡还是先有蛋。

可参考的旁证是 OpenDrop / Owl 这类项目在 Linux + 支持的网卡上做到过与 Apple 设备互通。但它们能否在当前 iOS 版本上工作、是否需要特殊处理，需要查证，不能想当然。

## 6. 建议的推进顺序

1. **先查门 1**：调研 OpenDrop/OWL 在近年 iOS 版本上的实际可用性，以及是否绕过了 Apple 身份校验。这一步不需要任何硬件改动，成本最低，但能不能继续做取决于它。
2. 门 1 若成立，再投入门 3（签名路线选择）。
3. 门 2 的验证（私有 OID 是否可用）放到最后，因为它需要先解决门 3。

换句话说：**现在最该做的不是继续逆向，而是确认这条链路在协议层是否对非苹果设备开放。**

## 7. 如果门 1 不成立

那么这个项目在"不加硬件、不开 Secure Boot"的前提下没有可行路径，应当正式结束，并把已有成果整理成一份完整的逆向记录——其中包括驱动的 OID 分派表、嗅探模式与 ETW 输出、IHV 通道结构，这些对后来者仍有价值。
